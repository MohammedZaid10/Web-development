In the Software Development Life Cycle (SDLC), testing is a critical phase to ensure the quality, reliability, and performance of the software. Different types of testing are performed at various stages to validate different aspects of the application.

Here’s a breakdown of the most common types of testing, categorized by their purpose and when they occur.

### I. Testing Levels (The V-Model Sequence)

These tests are typically performed in a specific order, corresponding to the stages of development.

1.  **Unit Testing**
    * **What it is:** The first level of testing, where individual components or modules of the software are tested in isolation.
    * **Who does it:** Developers.
    * **Purpose:** To verify that each small piece of code (a function, method, or class) works correctly on its own.
    * **Example:** Testing a function `calculate_sum(a, b)` to ensure it returns the correct sum for various inputs, including positive numbers, negative numbers, and zero.

2.  **Integration Testing**
    * **What it is:** After units are tested, they are combined into groups, and the interaction between them is tested.
    * **Who does it:** Developers or specialized QA engineers.
    * **Purpose:** To find defects in the interfaces and interactions between integrated components.
    * **Example:** Testing the login process where the UI module must correctly send user credentials to an authentication module, which then interacts with a database module.

3.  **System Testing**
    * **What it is:** Testing the complete and fully integrated software product as a whole.
    * **Who does it:** The QA team.
    * **Purpose:** To evaluate the system's compliance with all the specified functional and non-functional requirements. It's a "black-box" test, meaning the tester focuses on inputs and outputs without knowing the internal code structure.
    * **Example:** Testing an entire e-commerce website: Browse products, adding to the cart, applying a discount, checking out, making a payment, and receiving an order confirmation email.

4.  **User Acceptance Testing (UAT)**
    * **What it is:** The final stage of testing, where the software is tested in the "real world" by the intended audience or client.
    * **Who does it:** End-users, clients, or stakeholders.
    * **Purpose:** To certify that the system meets the business requirements and is ready for deployment.
    * **Types of UAT:**
        * **Alpha Testing:** Performed in-house by the organization's employees before the software is released to the public.
        * **Beta Testing:** Performed by a limited number of actual end-users in their own environment.

---

### II. Testing Categories by Purpose

These types of testing can be applied at any of the levels above (Integration, System, or UAT).

#### A. Functional Testing
This category focuses on **what the system does**, verifying that each function of the software operates in conformance with the requirement specifications.

* **GUI Testing:** Ensures the graphical user interface meets its requirements, checking elements like buttons, text fields, and menus.
* **API Testing:** Validates that the Application Programming Interfaces (APIs) work as expected in terms of functionality, reliability, and security.
* **Database Testing:** Checks the integrity of data in the database, ensuring data is stored, retrieved, and updated correctly.

#### B. Non-Functional Testing
This category focuses on **how the system performs**, testing the quality attributes and readiness of the software.

* **Performance Testing:**
    * **Load Testing:** Checks the system's performance under expected user loads.
    * **Stress Testing:** Pushes the system beyond its normal operating limits to see how it handles extreme conditions and whether it recovers gracefully.
    * **Scalability Testing:** Determines how well the system can scale up to handle an increase in user load.
    * **Endurance Testing:** Tests the system with a sustained, significant load over a long period to check for issues like memory leaks.

* **Security Testing:** Uncovers vulnerabilities, threats, and risks in the software application to prevent malicious attacks.

* **Usability Testing:** Evaluates how easy, efficient, and user-friendly the software is for the end-users.

* **Compatibility Testing:** Ensures the software works correctly across different browsers, operating systems, hardware platforms, and network environments.

* **Reliability Testing:** Assesses whether the software can perform its function without failure for a specified time in a given environment.

---

### III. Testing Related to Code Changes

These are specific types of tests run in response to modifications in the code.

1.  **Smoke Testing** (or Build Verification Testing)
    * **What it is:** A preliminary set of tests run on a new software build.
    * **Purpose:** To determine if the most critical functions of the program work. If the smoke test fails, the build is rejected immediately, saving the QA team's time. It answers the question: "Is this build stable enough for further testing?"

2.  **Sanity Testing**
    * **What it is:** A quick, focused test on a specific area of functionality that has recently been changed or fixed.
    * **Purpose:** To verify that the bug fix or new feature is working correctly and hasn't obviously broken its immediate surroundings. It's a subset of regression testing.

3.  **Regression Testing**
    * **What it is:** Re-running functional and non-functional tests after a code change.
    * **Purpose:** To ensure that new code, bug fixes, or other changes have not introduced new defects or broken any existing functionality. This is crucial for maintaining stability in continuous development cycles.

### Summary Table

Category         | Testing Type        | Purpose
-----------------|---------------------|------------------------------------------------------------
Testing Levels   | Unit Testing        | Test individual components in isolation.
                 | Integration Testing | Test interactions between integrated components.
                 | System Testing      | Test the entire application as a whole against requirements.
                 | User Acceptance     | Validate that the system is acceptable to the end-user/client.
                 | Testing             
-----------------|---------------------|------------------------------------------------------------
Functional       | GUI, API, Database  | Verify what the system does (features and functions).
-----------------|---------------------|------------------------------------------------------------
Non-Functional   | Performance,        | Verify how well the system performs (quality attributes).
                 | Security, Usability |
-----------------|---------------------|------------------------------------------------------------
Change-Related   | Smoke Testing       | Check if a new build is stable enough for further testing.
                 | Sanity Testing      | Check if a specific fix or change works as expected.
                 | Regression Testing  | Ensure new changes haven't broken existing functionality.

A successful SDLC employs a mix of these testing types to build a robust and high-quality software product.

============

In React, props (short for "properties") are a fundamental mechanism for passing data from a parent component to a child component.

Think of them as arguments you pass to a function, but for React components.

What Exactly Are Props?
1. Data Flow: They are the primary way to send data down the component tree. A parent component "owns" the data and passes it down to its children via props.

2. Read-Only: Props are immutable (read-only). A child component can read the props it receives, but it should never directly modify them. If the data needs to change, that change should originate in the parent component (etypically through its state) and then be passed down as new props.

3. Customizable and Reusable Components: Props enable you to make your components highly reusable. You can create a generic component (e.g., a Button component) and then customize its text, color, behavior, etc., by passing different props each time you use it, without rewriting the component's logic.

4. Any JavaScript Data Type: You can pass any valid JavaScript data type as a prop:
  Strings (<MyComponent name="Alice" />)
  Numbers (<MyComponent age={30} />)
  Booleans (<MyComponent isActive={true} />)
  Arrays (<MyComponent items={['a', 'b']} />)
  Objects (<MyComponent user={{ id: 1, name: 'Bob' }} />)
  Functions (<MyComponent onClick={handleClick} />)
  Even other React elements or components (<MyComponent><p>Child Content</p></MyComponent>) - this is often referred to as children prop.

How to Pass Props (from Parent to Child):
You pass props to a child component by including them as attributes in the JSX tag when you render the child component.

// ParentComponent.js
import React from 'react'
import ChildComponent from './ChildComponent';

function ParentComponent() {
  const userName = "Alice";
  const userAge = 30;

  return (
    <div>
      <h1>Hello from Parent!</h1>
      {/* Passing props like HTML attributes */}
      <ChildComponent name={userName} age={userAge} />
      <ChildComponent name="Bob" age={25} /> {/* You can also pass literal values */}
    </div>
  );
}

export default ParentComponent;

How to Receive and Use Props (in Child Component):
In a functional component, props are received as the first argument to the component function. It's usually an object containing all the passed props as key-value pairs. You can then access them using dot notation or object destructuring.

// ChildComponent.js
import React from 'react';

// Receiving props as an object:
// const ChildComponent = (props) => {
//   return (
//     <p>Name: {props.name}, Age: {props.age}</p>
//   );
// };

// Receiving props using object destructuring (recommended for clarity):
const ChildComponent = ({ name, age }) => {
  return (
    <div>
      <p>Hello, my name is {name} and I am {age} years old.</p>
    </div>
  );
};

export default ChildComponent;

https://react.dev/learn/referencing-values-with-refs#refs-and-the-dom

We only useRef when that value is not being rendered through the DOM, iof it is being rendered through the DOM and used for displaying then we should not use useRef, we can use useState for that purpose to render any value in DOM

1st use case of using useRef:
Sometimes we want our variables to persist its values when page re-renders

2nd use case of using useRef:
we can access any DOM element by using variable.current

Caveats 
  1. You can mutate the ref.current property. Unlike state, it is mutable. However, if it holds an object that is used for rendering (for example, a piece of your state), then you shouldn’t mutate that object.
  2. When you change the ref.current property, React does not re-render your component. React is not aware of when you change it because a ref is a plain JavaScript object.
  3. Do not write or read ref.current during rendering, except for initialization. This makes your component’s behavior unpredictable.
  4. In Strict Mode, React will call your component function twice in order to help you find accidental impurities. This is development-only behavior and does not affect production. Each ref object will be created twice, but one of the versions will be discarded. If your component function is pure (as it should be), this should not affect the behavior.

While using the <Script> component for inline code works, the more common and standard React pattern for running component-specific logic is still the useEffect hook.

next/script: Primarily designed to manage loading external, third-party scripts (like Google Analytics, Stripe, etc.), giving you control over when they load with the strategy prop.
